# Polaris — Infrastructure and Hosting Plan

Tender: AgriSETA Internal Audit Software Solution
Requirement: "The software proposal must have a plan, detailing how it supports the
following infrastructure requirements" — all 6 must be confirmed for points.

This document is that plan. Each requirement is answered with how Polaris meets it
and where the deployment will run.

## Proposed deployment

AWS region **Cape Town (af-south-1)** — keeps data in South Africa.

```
┌────────────────────────────────┐        ┌────────────────────────────────┐
│  App tier — EC2                │        │  Data tier — RDS PostgreSQL 16 │
│  Windows Server 2022 VM        │───────▶│  (or PG16 on a second EC2 VM)  │
│  - Node.js LTS + Polaris       │ 5432   │  - restricted to the app tier  │
│  - IIS (or NSSM) service       │        │    security group only         │
│  - HTTPS on 443 via IIS/ALB    │        │  - automated daily snapshots   │
│  - Task Scheduler: backup.ps1  │        │  - pg_dump exports to S3       │
└────────────────────────────────┘        └────────────────────────────────┘
```

Alternative: the same two-tier layout can be installed on **AgriSETA's own
Windows Server 2022 VMs** (on-premise or their existing cloud account) — the
software does not depend on any AWS-specific service.

## Requirement-by-requirement

### 1. Support cloud environment hosting — SUPPORTED

Polaris is a standard Node.js web application with no dependency on a specific
hosting platform. It will be deployed on AWS in the Cape Town region
(af-south-1). The same build runs on Azure, on a local hosting provider, or on
AgriSETA's own virtual machines — only configuration changes, no code changes.

### 2. Run on Windows Server 2022 or later — SUPPORTED

The application runtime is Node.js LTS on Windows Server 2022, installed as a
service via IIS (HttpPlatformHandler) or NSSM. The application also runs on
Linux containers, so the deployment is not locked to a single operating system.

### 3. Persistent data in SQL Server 2022 / MySQL 8.3 / PostgreSQL 16 — SUPPORTED

Polaris uses **PostgreSQL 16**, one of the three named databases. The data layer
is managed through the Prisma ORM; production DDL for PostgreSQL 16 is included
in the deliverable (`prisma/ddl/postgresql.sql`), and the application connects
to a remote database host through the `DATABASE_URL` connection string.

### 4. Data tier on a different VM from the presentation/logic tier — SUPPORTED

The proposed deployment is a two-tier architecture: the application runs on an
EC2 Windows Server VM; PostgreSQL 16 runs on a **separate** service (RDS) or a
second VM. The database accepts connections only from the application tier's
security group — no direct internet exposure. This split is the standard
deployment, not an exception path.

### 5. Daily backups with weekly and monthly reports — SUPPORTED

- **Daily:** RDS automated snapshots plus a scheduled `pg_dump` export (script
  `scripts/backup.ps1`, run daily by Task Scheduler) written to S3.
- **Weekly and monthly reports:** a backup-health report is generated by the
  backup job (success/failure, file size, age of newest backup, retention
  counts) and surfaced inside the application's admin area and by e-mail.
  *(Implementation note: the daily backup script exists; the weekly/monthly
  report is scheduled as part of the implementation plan — see "Honest gaps".)*

### 6. Backup retention for the 12-month contract — SUPPORTED

The backup script applies a retention policy of 1 095 days (3 years — the
contract plus support period) by default and purges older exports automatically.
Retention period is a configuration value and will be set to the contract
requirement.

## Authentication and access — honest position

- Users authenticate to Polaris with **email address and password**; passwords
  are stored bcrypt-hashed in the application's own database. No external
  identity provider is required.
- Active Directory / Entra ID **synchronisation** is supported through the
  REST API (`POST /api/v1/users/sync`): user exports are pushed on a schedule,
  matched by e-mail, and mapped to roles. Live SSO against AD/Entra is not
  claimed — the integration is file/API-based provisioning.
- All API access uses scoped API keys sent in the `x-api-key` header; every
  refused call and key lifecycle event is written to the audit trail.
- HTTPS is terminated at the load balancer / IIS on the app tier; HTTP requests
  are redirected to HTTPS in production.

## Honest gaps declared

- **Weekly/monthly backup reports:** the daily backup job and 3-year retention
  exist and are proven; the consolidated weekly/monthly *report* is scheduled
  for the implementation phase.
- **SQL Server / MySQL:** PostgreSQL 16 is the delivered database. DDL exists
  for MySQL 8; SQL Server support would follow the same ORM pattern if ever
  required — it is not part of the delivered configuration.
- **AD/Entra SSO:** directory *sync* exists; single sign-on against the
  directory is not built and is not claimed.

## Installation summary (Windows Server 2022, two VMs)

1. **DB VM / RDS:** provision PostgreSQL 16, create the `polaris` database and
   service account, apply `prisma/ddl/postgresql.sql`, restrict access to the
   app VM.
2. **App VM:** install Node.js LTS, copy the application, `npm ci`, set
   environment (`DATABASE_URL`, `AUTH_SECRET`, `CRON_SECRET`, mail settings),
   `prisma generate`, `npm run build`.
3. Install `next start` as a Windows service; bind HTTPS on 443 in IIS/ALB;
   open only 443 inbound.
4. Schedule `backup.ps1` (daily) and the escalation scheduler
   (`POST /api/escalation/run`) via Task Scheduler; schedule the directory
   sync script if AD integration is used.
5. Verify from a workstation: login, HTTPS redirect, API key call, backup file
   lands on schedule.
